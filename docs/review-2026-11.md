# rulecad library review, November 2026

A top-to-bottom review of the rulecad kit: every package's code, tests, documentation and packaging, and the path a
newcomer takes from an empty folder to a checked part. It records what was found, what was fixed alongside it, and
what is left, with a recommendation for each.

**The short version.** The kit's ideas are sound and unusually well carried through: traceable values, findings in
plain words, expressions that are parsed and never run, engineering formulas that check out against textbooks. Its
weak points are at the edges. Bad input mostly surfaces as an error from deep inside, or as a plausible wrong
answer. Several checks passed things they should not. The documentation is a reference with no way in. And the
release pipeline has been stopped since 31 October, so npm is ten versions behind the repository. About sixty
defects were fixed in the same pull request as this report, each with a test. The larger items left over are
listed in [What to do next](#what-to-do-next).

## How it was done

- **Scope:** all 16 packages under `packages/`, the repository's tests, scripts, workflows and documentation, and
  the two example workspaces. About 14,000 lines of library code and 5,000 of the `cad` tool.
- **Method:** each package was read in full and exercised with good, bad and hostile input. Claims in READMEs were
  run. Formulas were checked by hand and against the package's own solvers. Every defect listed as fixed was
  reproduced before it was changed, and has a test that fails without the fix.
- **Newcomer walk:** `npm create rulecad` was run as a stranger would, then a first part, a second, and an assembly
  were made by following only the published documentation.
- **Baseline:** line numbers refer to `main` at commit `7181c67` (the merge of pull request 102). Files changed by
  this review have moved a little since.
- **Limits:** the viewer was read, not run in a browser. The thin-picro board was checked from a cached build, not
  routed afresh. Windows was not available; Windows findings are from reading and are marked as suspected.
  The reference Python for the 88-line topology code could not be run (no numpy on the machine).

### Words used

| Word | Meaning here |
|---|---|
| Workspace | The folder a person's designs live in, with a `cad.config.json` |
| Object | One design: a `.json` of variables and a `.js` that draws the shape |
| Rule set | Shared facts with their sources: a printer's limits, a screw's sizes |
| Finding | One result of a check: a level (pass, warn, fail), words, and a code |
| Lamina | A flat mechanism drawn in one plane and printed in one piece (`@rulecad/flexures`) |
| Sandbox | The separate process a design's code runs in |
| Fixed | Changed in the pull request that carries this report, with a test |
| Open | Not changed; a recommendation follows |

## What is good, and should be kept

- **Traceability works end to end.** `cad why home/hook.hole` prints a value, its expression, and each rule it
  rests on with its source. All 170 published rule values carry a kind, a source and a date.
- **Messages for the common mistakes are excellent.** A misspelt rule gives
  `"m4.clearence": no rule "clearence" in m4 (projects/home/objects/hook.json: variables.hole.value)`: what, where,
  and the path to fix. A misspelt JSON key suggests the right one.
- **The engineering is right where it was checked.** The beam solver matches a cantilever to 1e-8 and the elastica
  to 0.1% up to a load parameter of 10. `elastica()` matches Bisshopp and Drucker to four figures. The
  finite-element cells pass patch tests exactly and converge to Timoshenko beam theory. Paros-Weisbord notch
  stiffness is within 2.2% of the integrated notch. Optimiser gradients are tested against finite differences.
- **Manufacturing files are well-formed.** Gerber format statements, X2 attributes, closed pours and outlines,
  mirrored bottom silkscreen, and separate plated and unplated drill files all parsed back correctly for three
  boards.
- **"Parsed, never run" holds.** No `eval`, `Function` or string timer anywhere. Link text reaches the page
  through `textContent`; drawings are shown as images.
- **Small, real tests of the hard promises.** A test checks that the small packages import nothing but each other.
  A test installs the packages as a stranger gets them. The release plan orders packages by dependency.
- **Design choices worth protecting:** findings as data with `--json`; the host abstraction that lets the core run
  on a workspace in memory; the content-keyed build cache; refusing to overwrite; both local servers bound to
  loopback; deterministic results.

**The tutorial** (`packages/cad/TUTORIAL.md`) goes from an empty folder to a wall hook checked against the screw it
hangs on, in seven steps. A test writes every file the tutorial gives and runs every command in it, and checks that
the mistakes it lists are reported in the words it quotes. It caught a wrong line number in its own first draft.

**A recommended path from small to complex**, which the tutorial's last section now points along:

1. The soap tray as given: check, why, set.
2. A part of your own from rules (the tutorial's hook).
3. A reference object and a fit assembly (the tutorial's screw).
4. Named parts, a support that breaks away, a second filament.
5. Variants, then a release, then a link.
6. Joints and poses, with a sweep.
7. A model from elsewhere measured into rules, and matched.
8. An optimised part with an analysis.
9. A board, then a case that reads it.
10. A lamina mechanism.

Steps 4 to 10 each have a README section and no worked example. Writing one for each, tested the same way as the
tutorial, is the largest documentation gain left.

## Findings by package

Severity is marked **high** where a check passes something it should not, a wrong number is returned without an
error, or a security promise is broken.

### cad, the command

| Finding | Severity | Status |

**Structure.** `bin/cad.mjs` is about 870 lines holding the dispatch, the stress analysis and its report writer, the
release logic and the optimiser's reporting. Dispatch is an `if` chain. This review replaced the three ad hoc
argument scanners' worst behaviour, but the right shape is one table per command (its options, which take values,
its positionals, its usage line), parsed once, with `--help` per command. The analysis and release code belong in
`lib/`, where they can be tested without starting a process. Other duplication: the schema-and-lint block is
copied between the object and board checks; `named` and `allowed` are each written three times in `assembly.mjs`.
`CadError` was used in one file; this review used it for the new errors, and the rest should follow.

**Tests.** Nothing covers `release`, `status`, `history`, `diff`, `printed`, `compare` or `variants`: the least
reversible part of the tool, since it commits and tags. The test helper merged output and discarded the exit code;
a second helper that keeps it was added and used for the new tests.

**Build time (added 7 Nov).** A launcher build took 22 minutes, 17 of them in the physics and 1.6 in the flooded
frame's probe, and any edit started it over: the build key hashed the `.json`'s text, so rewording a rule rebuilt
everything. Fixed in flexures 0.3.0 and cad 0.7.25: the physics and the probe are stages kept in `.cache/stages/`,
keyed by their inputs and the library's code (the sandbox reads them and hands back what it makes; `laminaCache`),
and the build key is the resolved values, not the text. A build that changes only a strap or a check, or a rule's
words, has the solve at once; `LAMINA_TIMES=1` prints each stage's time. Measured: cold 21 min 42 s, warm 3 min 11 s,
the same findings. Then (flexures 0.3.1) the kinematics (the sequence, states, holds, strain and stops) and the
frame's finite elements became stages too: warm 60 s, the same findings again. Still computed every build: the
frames for the animation (22 s), the flood fill (9 s) and the room check (9 s).

**Documentation.** The README says "no dependencies but JSCAD"; the package depends on `@rulecad/fea` and the
lamina needs `manifold-3d`. Later snippets use `pla`, `x1c` and `petg` without defining them. The shaped-curve
example was still running after twelve minutes of processor time, with no warning that it would. Eight finding
codes a user will see are missing from the table (`lamina.bridge`, `.guide`, `.frame`, `.across`, `.rigid`,
`.flood`, `.model`, `.physics`). The header of `lamina.mjs` lists six checks of about thirty.

**Structure.** `lamina.mjs` is five modules in one file, and `lamina()` is one function of about 890 lines with
some forty closures. A natural split is the plane's geometry, the finite-element peak, the kinematic checks, the
3D print builder and the flood, with each check a function from a shared context to findings. Smaller points:

- The block that walks the sequence's poses is pasted three times, and the same set of kinds is named twice.
- Thresholds are unnamed: `gap × 0.98`, `kept > 0.75`, `height − apex >= 2`, a 15° angle, a 50 N hand. A named
  table with sources would also let `check` override them evenly.
- Poisson's ratio is written into the code four times with two values (0.35 and 0.38). It belongs on the material.
- Lamina states are in degrees and every model is in radians.
- The spec's names collide: `free` against `loose`, `grip` against `grips`.
- The robust 2D helpers on manifold are private. So the launcher draws its own bodies with JSCAD's 2D booleans,
  with a comment working round an offset bug. Exporting `union`, `subtract`, `grow` and `shrink` on loops would
  let input drawing use the trusted kernel too.

**Tests.** 55 tests pass in about 15 minutes. One test takes 9.5 of them (seven runs of the catapult), and two
others two minutes each. The static cases pay for the full physics; `physics: false` there would cut most of it.
Lamina assertions are mostly "a fail with this code exists": they do not pin the passing findings, so a check that
stopped running would go unnoticed.

**Accuracy, measured.** Error against Timoshenko beam theory, by cells through the depth of a member:

| Cells through the depth | 2D cantilever | 2D simply supported | 3D cantilever |
|---|---|---|---|
| 1 | −32.6% | | |
| 2 | −11.2% | −11.0% | −12.5% |
| 4 | −3.2% | −2.9% | −5.0% |
| 10 | −0.7% | −0.3% | |
| 20 | −0.3% | +0.2% | |

The cells are right and converge. But two cells through a member is 10% too stiff and one is 32%, and nothing in
the documentation said so (both READMEs now carry this table). The optimiser's default filter of 1.5 cells invites members two or three cells thick.
This deserves a sentence in both READMEs and a warning from `analyse` when a member is thin on its grid.
The tests compare with Euler-Bernoulli theory, which is not what the cells converge to: the 3D test passes at +1.0%
today and would fail at +1.8% on cells half the size.

**Documentation.** "Matches the published 88-line code step for step": the tests assert the step count and the
first and last compliance, not each step. The fea README says the direct solver is quick up to about 100,000
cells; 448 × 224 took 52 seconds. The topopt README says faces steeper than the limit are tipped back; that only
happens with an option that is off by default. This matters: see the overhang finding under
[printcheck](#printcheck). Run times are not stated anywhere: the 3D README example is about twelve minutes.

**Structure.** `topopt.mjs` holds five concerns in 1,256 lines: regions and discretising, the model and
optimiser, the MMA optimiser, drawing, and clean-up. MMA and the drawing half share nothing with the rest. `lift`
is never called. The two packages disagree on argument shapes: fea takes a built grid and dof-indexed arrays,
topopt takes regions. The friendly region language (`at`, `r`, `size`, `fix`) exists only in topopt, so "how far
does this bracket bend" needs index arithmetic in fea. An `analyse(problem)` that takes shapes would close that.
The threads backend uses a different preconditioner from the plain one, so results differ in the tenth digit per
solve and the sixth after 25 optimiser steps. Each is repeatable; the difference should be documented.

## Across the whole kit

**One shape for results.** The packages agree on units (millimetres), on Z up, and on triangle winding. They do
not agree on what a result looks like:

| Package | Result |
|---|---|
| printcheck, flexures, cad | Findings: `{ level, text, code, values, at }` |
| model-link `check` | A list of strings |
| variables | A thrown error with `code` and `path` |
| versions | `{ kind, reasons }` |
| fit | A number, or `{ gap, at }` |

`at` means a box in printcheck, a point in fit, and four different things inside lamina findings. Settling on the
finding as the one result shape, with `at` always a point and `box` for a box, would let every tool that shows
findings show all of them. (Done 7 Nov: printcheck and lamina findings give `at` as a point, `box` for a box and
`between` for two places; model-link's `check` gives findings with code `link.data`; variables' coded errors and
versions' reasons were already of this kind.)

**One way to refuse bad input.** The best pattern in the kit is variables' coded errors and model-link's `decode`:
plain words, a code, the place. Most other packages let empty, null or wrong-type input fall through to a
`TypeError` or `RangeError` from inside, which breaks the kit's own rule of plain words. A small shared helper
(`need(name, value, what)`) at each public door would fix most of the remaining open rows above. (Done 7 Nov at
the doors the review named: flexures' models and sizers, shapes' features, fit's measures, printcheck, fea.)

**Options.** Printer keys mix `support_gap` with `onLayer`. Tolerances are positional in some functions and in an
options object in others. Diameter is `d` in one shape and `hole` in the rest.

**Duplication.** Vector helpers appear four times, bounds three times, point-in-solid three times, and the
point-to-triangle routine twice. For model-link and the viewer that is the deliberate price of having no
dependencies. For fit it is not: it already depends on printcheck. There are three LU solvers across flexures and
fea.

**Types.** Several JSDoc blocks have drifted away from their functions, so the generated types say `any`:
`bounds` and `shape` in printcheck, `discretise` and `model` in topopt, `flexureMaterial` in flexures. The types
are generated at publish and never checked for `any` on exports; a test could.

**File size.** The one-file-per-package rule served the small packages well. Three files have outgrown it:
`lamina.mjs` (1,361 lines), `topopt.mjs` (1,256) and `pcb.mjs` (1,269), each holding four or five separable
concerns. (Lamina was split on 7 Nov: see item 7 under What to do next.)

**Tests and continuous integration.** The suites pass on Linux, macOS and Windows. Three things would make them
catch more:

- Test the checks for failing, not only for passing. Most of the high-severity rows above were checks that passed
  what they should not, and their tests asserted only the passing case.
- Test formulas against the solver, not against themselves. The cartwheel test asserted the formula as written.
- Keep README numbers honest by test. Two were wrong in flexures; the tutorial's approach generalises.

The whole run takes about 20 minutes locally, 15 of them in flexures.

## What was changed alongside this review

Every item has a test that fails without it.

- **create-rulecad:** new workspaces get today's `cad`; the folder is told apart from `--share`'s value; any
  folder name makes a package name npm accepts.
- **cad:** errors that name the file and line; unknown variables, empty results, broken JSON; `--version` and
  `--help`; misspelt commands and options refused by name; options in any order; `--set` values kept whole and
  kept out of paths; JSON edits that keep line endings and indentation; `status`, `preview`, `release` and
  `printed` fixes; the sandbox tightened and described honestly; library modules exported.
- **A tutorial**, replayed by the tests.
- **printcheck:** sustained overhangs caught; 2 to 25 times faster with identical results; input validated.
- **model-link:** limits enforced before unpacking; the 3MF title; `keep`.
- **variables:** names looked up as an object's own; clashes and bad values refused.
- **versions:** role, unit and range changes reported.
- **flexures:** hinges in laminas; the solver's tolerance; the cartwheel formula; curves; placed modules; README
  numbers; browser safety; complete type declarations.
- **fea:** input validated at the door; an under-held part named.
- **keyboard-layout:** one-row imports.
- **rules:** a test for every value; the README's table completed.
- **Repository:** the zero-dependency test covers every shipped module; the types script verifies what would be
  published; documentation corrected.

Three behaviour changes to be aware of. A design that reads a variable that is not there now stops, where it used to
build from `undefined`; none of the 112 local designs does this, and a name set only for the on-screen copy is
still allowed. `cad check` warns on sustained overhangs it used to pass. And a lamina whose frame can slide or turn under its
springs' loads gets a `lamina.frame` warning asking for a `grip`.

## What to do next

In order of what it unblocks.

1. **Publish.** Two packages need a first publish by hand, each asking for two-factor in the browser. Then the
   workflow can run again:

   ```sh
   node scripts/types.mjs
   npm publish --workspace packages/flexures --access public
   npm publish --workspace packages/smooth --access public
   npm trust github @rulecad/flexures --file publish.yml --repo JoniBach/rulecad --allow-publish --yes
   npm trust github @rulecad/smooth --file publish.yml --repo JoniBach/rulecad --allow-publish --yes
   gh workflow run publish.yml
   ```

   Consider letting the release plan hold back only new packages and what depends on them, so that one new package
   no longer stops every other release. It keeps the plan's own rule, that nothing lands on npm before what it
   needs.

2. **The checks that pass what they should not.** Done 7 Nov, all four: the board's fab checks (ring, via,
   silkscreen, measured from the board against the rule set); the keyboard recipe on small matrices; `fit` on
   intersecting parts; 2D multigrid with rollers. Added the same night, from the launcher's prints: ledges held on
   one side, and parts too close on the first layer (printcheck 0.2.0).

3. **Warn when the finite-element grid is too coarse.** Both READMEs now give the measured table (done with this
   review). Done 7 Nov (fea 0.2.7): `analyse` returns `thin` (the share of the part an opening of two cells takes
   away: its members under four cells thick), and `cad check` warns (`fea.coarse`) when that is over 5%, naming the
   cell to try.

4. **The optimised bracket's overhangs.** Measured 7 Nov: with the surface's tipping-back step on (`outline.tip`,
   now a problem option in the schema) the bracket's sliced overhang is the same 160.3 mm², so the step is not the
   remedy and stays off by default, as the topopt README says. The lean is in the optimised shape (facets of 55°
   to 70° from the density field's grey cells); the warning is true, and a fix belongs in the optimiser's overhang
   filter or in a different build direction for that example.

5. **Worked examples for steps 4 to 10 of the path**, each replayed by a test as the tutorial is. Done 7 Nov:
   `packages/cad/EXAMPLES.md`, seven examples (parts with a breakaway brim and a second filament; variants and a
   release; a lid on a hinge with poses and a sweep; a model measured into rules and matched; an optimised arm
   analysed; a four-key board; a flicker mechanism animated), sixteen files and eighteen commands, replayed by the
   same harness as the tutorial with a check on what each promises.

6. **One result shape and one way to refuse input**, starting with `fit` and the model functions in flexures. Done
   7 Nov (see Across the whole kit).

7. **Split the three large files**, lamina first: it is the one changing fastest, and its tests are the slowest.
   Done for lamina, 7 Nov (flexures 0.3.1), with no change of behaviour: `plane.mjs` (the 2D geometry on manifold,
   the transforms, the print in 3D and the shared constants, 166 lines), `bent.mjs` (a flexure drawn bent and its
   finite-element peak, 137), `flooded.mjs` (the flooded frame, 106), and `lamina.mjs` down from 1,446 lines to
   1,062. What is left is `lamina()` itself, about 950 lines of stages sharing one scope; the next cut would make
   each stage a function over a context object, with the stage cache keyed on that context. `topopt.mjs` and
   `pcb.mjs` are untouched.

8. **Tests for releases** in `cad`, on all three platforms, before the next change to that code. Done 7 Nov: a test makes a git workspace, releases, changes, releases the bump, rebuilds the earlier release from its tag, diffs the two and reads the changelog; it runs in CI on Linux, macOS and Windows.
